# The gate scenes CI runs on every pull request, one per line, blank lines and #comments ignored.
#
# WHY THIS IS A FILE AND NOT A LIST IN THE WORKFLOW: it lives next to the gates, so adding one is a
# one-line change in the same commit as the gate itself rather than a second edit somewhere else that
# is easy to forget. `.github/workflows/gates.yml` reads it.
#
# WHAT BELONGS HERE: a scene that ends with `get_tree().quit(0 if _fail == 0 else 1)` and that has been
# watched printing a green verdict. Every entry below was run before it was added — a list that fails for
# reasons unrelated to the change is worse than no list, because the first red run teaches everyone to
# ignore it.
#
# DO NOT JUDGE A GATE BY ITS EXIT CODE. Several of these intermittently segfault at SHUTDOWN, after
# printing a pass: SimPhase65SelectorGate did it on 3 runs in 4 on 2026-08-19, and SimPhase5Gate and
# SimPhase55Gate do it too. Sampling exit codes a handful of times looked clean, which is exactly how an
# intermittent fault hides. The workflow keys on the printed verdict and reports a post-verdict crash as
# a warning; fixing the crash itself is its own job and nobody has done it.
#
# WHAT DOES NOT BELONG HERE: the probes and diagnostics. `PreviewSimDiag` and `SimProfile` assert
# nothing and print measurements; `SimProfile` is a BENCHMARK and needs the user's go-ahead (§11, §14),
# which a CI runner cannot give. The various *Probe scenes are investigation tools, not criteria.
#
# Not yet included, and not because they fail — they have simply never been run to a verdict here:
# PoolClipmapWarningProbe, StreamBankSurfaceCheck, StreamCustom0Probe, WaterGeometryParamsCheck.
# Add them once someone has watched one go green.
#
# WaterBodiesPhase4Gate WAS on that list, recorded as hanging. It was not hanging: its _settle()
# awaited RenderingServer.frame_post_draw, which never emits without a display server, so every
# headless run stopped inside section A having printed only its heading. _settle now waits on
# process_frame when there is no renderer, and the headless output is identical to the windowed
# output line for line — same vertex counts, same wave deltas, every control still firing. It is in
# the list below.

# P4b - the lane graph and the four queries a naive consumer needs (SS6.4). Grows with the phase; it
# starts at the cross-section because a connector joins two lanes and a stop line sits at the head of
# one, so an error there surfaces everywhere else as something that looks like a junction bug. The
# lanes tile the carriageway exactly, traffic_side decides which lanes are oncoming and does it the
# right way round, a one-way road has none, and an offset finds exactly one lane at every boundary.
# Then the graph itself: every incoming lane reaches one straight, one left and one right on the other
# arms and no U-turn on its own; a connector leaves and arrives along the headings of the lanes it
# joins, measured on the curve rather than on the control points; traffic_side decides which turn
# crosses oncoming traffic; and every incoming lane has a stop line on the footprint boundary that
# moves when the trim-back does.
bench/RoadLaneGraphGate.tscn

# P4b - the COMPLETENESS bar, not the correctness one. Every other road gate is written in the road
# system's own vocabulary, so it can only ask questions the road system already knows how to answer;
# sufficiency is the opposite question - what does a consumer need that nobody thought to publish? The
# only way to find out is to write the consumer, so this drives bench/reference/road_lane_follower.gd,
# a vehicle that follows lanes, holds at junctions and yields using nothing but the four published
# queries. It asserts that the follower never names a solver (read from its source, because a consumer
# that quietly compensates still works), never needs data it cannot get, actually arrives, holds for
# priority traffic but not for traffic without it, obeys a signal without reading the ABSENCE of one as
# either colour, and never teleports across the road-to-connector handoff. Writing the follower found
# three gaps, all closed in the data: a stop line with no arc length, a lane_stop that answered with
# the first junction rather than the next, and a road that would not say how long it was.
bench/RoadSufficiencyGate.tscn

# P5a - TIER FAR (§10): the road as terrain. Because P1/P2 put the road INTO the heightmap, a distant
# road needs no mesh at all - only a statement of what the surface is made of, painted into the
# terrain control map, where it LODs with the terrain and has nothing to pop. This gates the two halves
# that are decidable from numbers: the coverage the grader computes (solid to the edge of formation,
# smoothstepping out over the shoulder) and the control words the paint kernel packs from it, asserted
# against literal bit shifts rather than the kernel constants. It also checks that a paint preserves
# the base texture and the hole bit, that a bare cell is not written at all (writing weight-zero still
# claims the cell for the layer, which would surround every road with dead ground), and that roads
# paint in ASCENDING priority - the one part of the wiring that is checkable without a terrain, and the
# one that is silently wrong, since the wrong order still paints a complete road, just the other one.
bench/RoadPaintGate.tscn

# P5b - TIER MID (§10): the chunked ribbon mesh, where tier FAR stops being enough. Every claim §10
# makes about chunking is arithmetic, so none of it needs a rendered frame - and a rendered frame is the
# worst way to check a crack a millimetre wide. Chunks are cut where terrain REGIONS are, so a chunk and
# the region under it live and die together (control: a different region size moves every cut; a 45°
# road must be cut on both axes). Seams are compared for EXACT equality, not to a tolerance: `ring` is a
# pure function of arc length, so two chunks meeting at the same s compute the same floats - a mesher
# accumulating s += step per chunk would agree to six decimals, pass any tolerance, and crack. Nothing
# chunks across a junction footprint (controls: something DID cover it without the footprint, and the
# road either side is still built). LOD coarsens monotonically and the carriageway never narrows, with
# camber dropped before shoulder as §10 orders. The ribbon height is checked against the GRADER rather
# than against a formula written out here, because drifting from the grader is the only way it can go
# wrong and a copy of the formula would drift with it. UVs run in metres, so a chunk boundary does not
# rescale the road markings.
bench/RoadMeshGate.tscn
